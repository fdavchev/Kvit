**What exists that matters here (verify in the code, do not trust this summary):**
- **Saved copy of server data** (Phase 8b): the TanStack Query cache is saved in IndexedDB with `idb-keyval` for 24 hours, wiped when the signed-in person changes (`core/auth/keepCacheToOnePerson.ts`, the only place that wipes), version string `savedQueryCacheVersion` (now 5), 3-second limit on reading it, and the "Updating…" note on the main tabs.
- **`ClientRequestId` (a GUID the phone makes) with a unique index** on expenses, settlements and personal entries. A repeated request returns the first result; two requests at the same moment both succeed (DECISIONS Phase 8 and 9; personal entries since Phase 13). No table changes are needed for the outbox, and probably no migration at all.
- **Error mapping:** 502, 503, 504 and "no answer" all map to `errors.network` ("The server may be waking up…"); 4xx are never retried by the query client except 408 and 425; refusals carry error codes (`ResultCodes`, `errors.*` in en.json and mk.json, `core/api/errors.ts`).
- **Rate:** an expense or personal entry gets its exchange rate when the server saves it (looked up last, inside the transaction), not when the phone typed it.
- **Reusable pieces:** `useSaveOnce`, `KvitSheet`, `KvitForm`, `AmountField`, `KvitAmount`, the toast pattern (Sonner), `refreshPersonalEntries`, the expense cache helpers (`expenseCache.ts`, `groupRefreshAfterMoneyChange`), `savedQueryCache.ts`.
- Guests have no Budget (403 on personal endpoints), so a guest can only queue group saves.
- `/health` never touches the database, and nothing polls Neon.

**Goal (from the ROADMAP, DECISIONS and SCREENS; check the docs):**
1. **A queue in the browser** (IndexedDB, its own small module `outbox/`, per signed-in person, wiped or kept apart with the same one-person rule as the saved copy): every queued action has the `ClientRequestId` made on the phone, is stored before anything is sent, survives closing the tab, and is sent in order, one at a time, as soon as the server answers.
2. **What can be queued in the first version** (DECISIONS): new expenses (including One bill), new personal spending and income, and "Marko paid me" payments. Edits, deletes and Undo are **not** queued (BACKLOG, later).
3. **On screen:** a queued item appears in its normal list at once, marked "not synced yet"; a small place that says how many changes are waiting; when the queue is empty after sending, the in-app message **"All up to date ✓"** (a toast or a small bar, Filip picks); a failed item says **"1 change couldn't be saved"** with the reason (the translated error text) and **Retry** and **Discard**.
4. **When to send:** on app open, when the browser says it is back online, when the tab becomes visible, and after a failed send with a back-off; the first send also wakes the server. Never poll Neon, never more than one request at a time, and `/health` may be used to wake the server only if it does not change the rules above.
5. **Not in this phase:** queuing edits, deletes or Undo, the admin statistics page (Phase 18), future and planned payments, recurring expenses, pushing notifications, a service worker or installable app.
6. **The phone layout comes first** (360 px, then the 64rem desktop layout), EN + MK, light and dark, glass popups for sheets, animations only transform and opacity and off under `prefers-reduced-motion`, skeletons while loading, `KvitAmount` for displayed amounts, the app's money formatter (English "MKD", Macedonian "ден."), never the word «курс» in Macedonian (use «цената на еврото»).
