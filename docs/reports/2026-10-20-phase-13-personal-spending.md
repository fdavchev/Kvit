# Phase 13: personal spending + custom categories (report)

_Written 2026-10-20. Branch `feat/13-personal-spending`. Release 2 ("budget"), first phase._

## What you can do now
- **Add personal spending:** Budget tab "+" (category, amount, Save: 2 taps + 1 field) or Home "+" > "Personal spending" (4 taps + 1 field). Currency starts as the currency of your last entry (MKD the first time). Date is today, changeable within the last 24 months. Optional note.
- **Your own categories:** "+ New" in the category grid opens a sheet at once (name, emoji, colour); the new category is picked and you go on to the amount. "Edit my categories" (rename, archive with Undo, bring back) is in the same grid.
- **Budget tab (`/budget`, between Groups and Settings):** month strip (last 24 months), "Spent this month" card, a tile per category with its total, the entries (tap one to edit or delete it; Undo after delete).
- **Guests** (joined without an account) do not get the Budget tab, the Home item or the API; they are sent to Settings, where "Make an account" is.

- `PersonalEntries`: the `personal_entries` table.

- **Code review (2026-10-20, `/code-review high`, 8 findings, Filip: fix all 8):**
  - **Dates (finding 1, Filip: last 24 months up to today):** personal spending dates are limited to the 24 months the Budget strip shows. Frontend: `features/budget/budgetMonths.ts` is the one place that says 24 (`budgetMonths()`, `earliestBudgetDate(today)`); `DateSheet` got optional `earliestDate` / `latestDate` (defaults keep the expense rule). Server (`PersonalEntryFields`): earliest = first day of the month 23 months before the UTC month minus 1 day; latest = UTC today plus 1 day (the user's today can be a day ahead of UTC); an edit that keeps the existing date is not range-checked (`CreateForEdit`). Expenses keep their old rule. Known edge: just after a new UTC month starts, a person west of UTC (for example New York) can be offered the first day of the earliest month, which the server refuses; east of UTC (Skopje) is fine. The future and planned payments idea stays in BACKLOG.
  - **Month query (2):** `?month=` before 2000-01 or after 9999-11 answers 400 `PERSONAL_ENTRY_MONTH_INVALID` (it used to throw and answer 500 for 9999-12).
  - **Rate inside the transaction (3, 4a):** `AddPersonalEntry` checks the duplicate first, then the fields and the category, and fetches the exchange rate last, inside the unit of work; `EditPersonalEntry` fetches the rate itself, only when the stored currency really differs, so a currency change by another device at the same moment no longer throws (the handler no longer reads the currency; `FindCurrencyAsync` was deleted). Cost: a slow NBRM call now happens inside the transaction (it holds no row locks while waiting, and a rate fetched in a rolled-back save is lost). `AddExpense` still fetches the rate before its duplicate check (the same flaw, left alone because expenses were out of scope; question for Filip below).
  - **Resend after delete (4b):** a repeat of an add whose entry was deleted since answers 400 `PERSONAL_ENTRY_CLIENT_REQUEST_ID_USED` (the id is used up; a 404 on a POST would look like a wrong address, and saving again would bring back something the person deleted).
  - **Unique category names in the database (5):** migration `PersonalCategoryNameUnique` adds a partial unique index on (`owner_user_id`, `lower(name)`) where the owner is set and `archived_at` is empty, written as raw SQL (EF cannot describe `lower(name)`). `DuplicateSaving` maps the Postgres duplicate error on that index to `CATEGORY_NAME_TAKEN` for create, update and bring back at the same moment (answered straight, not run once more, because a name Postgres sees as equal and C# does not, like İ against i or the Kelvin sign, would fail again with 500). Cyrillic lower-casing was checked in a throwaway Postgres 18: the default `en_US.utf8`, `C.utf8` and `pg_c_utf8` lower-case Cyrillic; only the plain `C` collation does not. Neon's `lc_ctype` is NOT VERIFIED (`SHOW lc_ctype;`); if it were plain `C`, the index would catch only Latin case variants at the same moment, and the C# check still catches Cyrillic in normal use. The migration fails if someone already has two active categories that differ only in letter case (none expected; check query in the report).
  - **Emoji (6):** trimmed on the server and in the browser; refused with `CATEGORY_EMOJI_INVALID` when every remaining character is plain ASCII; the 16-unit limit is counted after trimming. A single Cyrillic or accented letter therefore passes (a stricter symbols-only rule would wrongly refuse real emojis such as ‼️ and 〰️). *Rejected:* a symbols-only rule.
  - **Save and Delete together (7):** the sheet uses one shared `useSaveOnce` guard for add, edit and delete; while any of them runs, Save, Delete and the date, note and Category chips are disabled and dimmed.
  - **Own error codes (8):** `PERSONAL_ENTRY_CURRENCY_INVALID`, `_AMOUNT_NOT_POSITIVE`, `_AMOUNT_TOO_LARGE`, `_NOTE_INVALID`; the shared `ExpenseFields` checks take the code as a parameter, so expenses keep their `EXPENSE_*` codes. `MONEY_NOT_ON_CURRENCY_STEP` stays shared. `PERSONAL_ENTRY_DATE_INVALID` now reads "Pick a date from the last 24 months, up to today." (Macedonian draft).
