## What Phase 6 delivered
- **Google sign-in** on the live site: "Continue with Google" (Google's own white button, drawn once per language). The API checks Google's ID token (signature, issuer, audience, expiry, verified email) and links the person by Google's permanent id in `user_logins`. No migration was needed.
- **Never an automatic merge** with a password account: the same email gets a pop-up "This email already has an account." (Log in with password / another Google account / Close).
- **First Google sign-in** asks the name once, pre-filled from Google ("Almost there"). A Google account can add a password later in Settings ("Set a password"). A Google-only account that types a password gets a pop-up and never counts toward the lock.
- **Privacy page** `/privacy` (public, EN + MK, 7 short sections) and a small Privacy link on Welcome and in Settings.
- **Security headers** from Cloudflare `public/_headers` (CSP that allows Google's script, frames and style; COOP `same-origin-allow-popups`; `nosniff`; referrer policy). The `/api/*` proxy is untouched. The inline theme script moved to `public/theme-boot.js`.
- **Welcome:** pitch line removed, a small "or" between the Google button and "Sign up with email".
- **Polish found on the way:** no white box behind the Google button in dark mode, no layout jump, instant language switch of the Google button, faster EN/МК pill, Settings Log out always at the bottom.
- **`scripts/start-local.ps1`:** start, `-Check` and `-Stop` for the whole local app.
- Docs: guide `guides/phase-06-google.md`, the mockup `design/2026-10-03-google-sign-in/index.html`, SCREENS, BACKLOG, ARCHITECTURE traps.

## Known risks and leftovers
- **Deploy order at the merge:** Cloudflare publishes the new site a few minutes before CI finishes the Render deploy. Until the API answers with `hasPassword`, the strict `parseMe` rejects the old answer and the site shows an error. Merge, then wait for the green CI.
- **Preview deployments can't sign in** (origin not authorized): expected.
- **The Google button's hidden-slot and overlap fixes lean on Google's undocumented markup;** if Google changes it, the button may jump again (a clipped, fixed-height box limits the damage).
- BACKLOG holds: the Google 401 treated as "session ended", one Google callback per page, "Same as device" not followed live by the button (no longer relevant: the button ignores the theme), the 559 kB main bundle, a privacy contact email before Kvit grows, safe Google-to-password linking, changing the display name.

## Decisions and rejected alternatives (moved word for word from DECISIONS.md on 2026-10-03)
## 2026-10-03: Phase 6 (Google sign-in + privacy page): decision log, in progress
Facts were checked on 2026-10-03 against Google's guides (CSP/COOP, FedCM, ID-token checks), the Cloudflare Pages `_headers` page and the `Google.Apis.Auth` source and NuGet page. No migration is needed: `user_logins`, `users.google_picture_url` and `SignUpMethod.Google` already exist.

**Filip's answers (product)**
- **Same email already has an account:** a pop-up on Welcome says "This email already has an account." (the address is not shown) with three buttons: **Log in with password** (opens Log in with the email typed), **Use another Google account**, **Close**. Never merged automatically (the 2026-09-25 rule stands).
- **First Google sign-in asks the name once, pre-filled with the Google name,** then Continue → home. *This replaces the "1 tap" in `SCREENS.md` screen 1 for the first time only; Filip chose it knowing the extra tap.*
- **Google accounts can add a Kvit password, in Settings only** ("Set a password" instead of "Change password" until there is one). A password log-in on an account without a password shows a pop-up: this account signs in with Google (**Continue with Google** / **Close**); those tries never count toward the 5-try lock. *Rejected:* the usual "wrong email or password" (the person guesses until stuck); an optional password box on the name screen (more to read the first time).
- **Privacy page names no email, "ask Filip"** (friends and family only). Before Kvit grows, Claude asks Filip for a contact email (BACKLOG).

**Technical choices (Claude decided)**
- **Token check: `Google.Apis.Auth` 1.77.0** (Apache-2.0), `GoogleJsonWebSignature.ValidateAsync` with `ValidationSettings.Audience = [clientId]`. Per its source it checks the signature (Google's keys, cached an hour), `iss`, `exp`, `iat` and `aud`, and throws `InvalidJwtException`. **`Audience = null` switches the audience check off**, so a missing client id stops the app at start-up. We also require `email_verified` and identify people by `sub`, never by email (Google's rule). *Rejected:* hand-written key-set checking (more code, more to get wrong).
- **`IGoogleTokenChecker`** in Contracts, `GoogleTokenChecker` in Infrastructure; tests use a `FakeGoogleTokenChecker`. Only `InvalidJwtException` becomes `AUTH_GOOGLE_TOKEN_INVALID`; failing to reach Google's keys stays a 500 with its cause (no silent fallback).
- **Client ID lives in the repository** (`appsettings.json` `Google:ClientId`, `src/web/.env` `VITE_GOOGLE_CLIENT_ID`): a client ID is public (it is in every page's HTML), not a password. *Rejected:* Render and Cloudflare variables (two dashboards, a redeploy after each change, values that can drift apart). The "never in the repository" rule is for passwords, keys and connection strings; the client SECRET is never used.
- **Endpoints:** `POST /api/auth/google` (existing link → signs in; no account → 404 `AUTH_GOOGLE_NO_ACCOUNT`; other account with the email → `AUTH_GOOGLE_EMAIL_TAKEN`; bad token → 401 `AUTH_GOOGLE_TOKEN_INVALID`; unverified email → `AUTH_GOOGLE_EMAIL_NOT_VERIFIED`), `POST /api/auth/google/sign-up` (token + name → creates the account with no password, the `user_logins` row and the `SignedUp`/`Google` event in one transaction; an already-linked `sub` just signs in), `POST /api/auth/set-password` (signed in; `AUTH_PASSWORD_ALREADY_SET` if one exists). New code `AUTH_USES_GOOGLE` for a password log-in or change-password on an account with no password, answered before any password check. Rate limit: the existing "log-in" policy. *Rejected:* `SignUpLimitFilter` (it only reads `RegisterRequest`, and every Google token needs a real Google account).
- **`MeResponse.hasPassword`.** At the merge Cloudflare shows the new site a few minutes before CI finishes the Render deploy; until then the strict `parseMe` rejects the old answer and the site shows an error. Accepted (family app; Filip merges and waits for the green CI). *Rejected:* two PRs, or an optional field (a silent fallback).
- **Headers: Cloudflare `public/_headers`** (CSP, COOP `same-origin-allow-popups`, `nosniff`, referrer policy). Cloudflare: headers in `_headers` are not applied to Pages Function responses, so `/api/*` is untouched; the Vite dev server and Scalar are not on Pages. FedCM stays off (optional, Chrome only), so COOP is needed. The inline theme script moves to `public/theme-boot.js` because the CSP forbids inline scripts. `style-src` keeps `'unsafe-inline'` (Sonner and React `style=`). *Rejected:* API middleware (the API serves no pages); a CSP `<meta>` tag (cannot set COOP or `frame-ancestors`).
- **Step 1 details (built 2026-10-03):**
  - Order of checks, Google log-in: token (401) → email verified (400) → time zone (400) → linked `sub` signs in → same email (any letter case) → `AUTH_GOOGLE_EMAIL_TAKEN` → else 404 `AUTH_GOOGLE_NO_ACCOUNT`. Google sign-up: token → verified → name/language/time zone → linked `sub` returns that account (nothing else touched) → create. Set password: password rule → `AUTH_PASSWORD_ALREADY_SET`.
  - A Google log-in never changes the password lock: a locked password account that is linked still signs in and its lock stays as it was.
  - The picture is refreshed from Google on every Google log-in (null included).
  - After `set-password` the handler signs the person in again, because adding a password changes the security stamp (same as change-password).
  - Besides `InvalidJwtException`, the three exceptions the library throws while parsing a malformed token (`ArgumentException` for an empty one, `FormatException`, `JsonReaderException`) also answer 401 `AUTH_GOOGLE_TOKEN_INVALID`; found by trying the real library, so junk can't cause a 500. Network failures stay 500.
  - A token missing `sub`, `email` or `name` fails loudly (500 naming the scopes), no silent default.
  - Two sign-ups racing with the same Google `sub` can give one 500; not handled on purpose (rare, not silent).
- **Step 2b details (built 2026-10-03):**
  - Dialog = **Base UI Dialog** (focus trap, scroll lock, hidden background) inside `KvitDialog`. *Rejected:* a hand-made dialog (none of those); the shadcn dialog file (needs the new package `lucide-react`).
  - One shared hook `useGoogleSignIn` runs the whole Google flow for Welcome, the "taken" pop-up and the Log in pop-up. Success → cache, the account's saved language, home. `AUTH_GOOGLE_NO_ACCOUNT` → `/signup/google` carrying the token in router state (a reload loses it and goes back to Welcome). `AUTH_GOOGLE_EMAIL_TAKEN` → the pop-up on Welcome; on Log in (no pop-up there) an error toast.
  - The Log in "uses Google" pop-up comes from the log-in error itself; Close clears the error.
  - Settings reads the person with `useMe()` so it cannot crash while logging out. Set password skips its "already has a password" redirect once saved, so it doesn't flash.
  - The Google button is as wide as its box (max 400 px); it is drawn once per language slot and never redrawn (see the button decision below); a failed script load removes the tag so the next screen retries; a missing client id shows the "couldn't load" text and logs the cause.
  - `readGoogleProfile` decodes the token only to show the name and email; the server is the one that checks it.
  - Headers file as in the plan, no `font-src` (fonts are same-origin). `src/web/.env` holds the public client id and is un-ignored in `.gitignore`.
- **The Google button is Google's own drawn button** (the ID-token flow has no custom-button option); only its theme, shape, text, width (max 400 px) and language are ours. **Filip picked the white (outline) look, and on 2026-10-03 decided it stays white in BOTH light and dark mode** (he first asked for black in dark mode; that was dropped because a theme change makes Google draw a new button, which flickered and could stay on Google's Macedonian placeholder), with the text "Continue with Google". The button is drawn once per language (English and Macedonian, stacked in the same place, one shown) and is never redrawn after it loads; a language switch only swaps which one is visible. *Rejected:* redrawing on every language/theme change (measured: a 36 px layout jump and 0.4-0.9 s delays); pre-drawing four versions (2 languages x 2 themes, more frames for a look Filip did not need). *Rejected:* our own peach button plus the One Tap prompt (Google may decide not to show it, so a tap could do nothing); a different Google flow that works with a custom button (more code and a second server check, and it drops the ID-token design).
- **The Welcome line "Only you need an account. Friends can be just names." is removed (Filip, 2026-10-03):** too long once translated to Macedonian. It came from the 2026-09-25 business review (it told newcomers that friends need no account); where that idea is explained instead (e.g. on the invite and group screens in Phase 7) is open.
- **Welcome shows a small "or" (МК "или") between the Google button and "Sign up with email" (Filip, 2026-10-03):** plain centred text, 13 px, no lines (he disliked the lines), equal space above and below. The word is `welcome.or`. Also: the Google button's box is marked `color-scheme: light` (Tailwind `scheme-light`) because in dark mode Chrome paints a white box behind Google's light-scheme iframe (found by experiment in Chrome 154; headless Edge did not show it).
- **A small "Privacy" link on both Welcome and Settings (Filip, 2026-10-03)**, so Google's rule (privacy link visible near sign-in) and the SCREENS.md Settings link are both met. Filip approved all Macedonian lines of Step 2a (the 18-line table, and line 17 as `Use "Change password".` / `Користи „Промени лозинка“.`).
- **Inside the "email already has an account" pop-up** Google's button can only read "Continue with Google" (its text is one of four fixed options), so "Use another Google account" becomes a small label above that button, and the picker lets the person choose another account.
- **The privacy page does not name Google's internal ID number** (Filip, 2026-10-03: people don't know what it is and it could put them off); it says Kvit receives only name, email address and profile picture link.
- **Google button: no layout jump (measured with headless Chrome 154 driven over the DevTools Protocol, 2026-10-03).** Every `renderButton` makes Google insert a wrapper `[placeholder (400x40, plain HTML, text in Macedonian whatever our language), iframe 0x0]`; the iframe loads 0.3-0.9 s later and for 1-2 frames both showed stacked, growing the box 44 → 80 px and moving everything pinned to the bottom 36 px. Fix: the two language slots overlap in one grid cell; each slot has a fixed height (`h-11`, `overflow-y-clip`) and Google's inner placeholder and iframe share one cell (`[&>div]:grid [&>div>*]:[grid-area:1/1]`; this depends on Google's undocumented markup, the clip is the safety net).
- **The hidden language slot is `opacity-0 pointer-events-none inert aria-hidden`, not `visibility:hidden`:** measured, Chrome does not let a `visibility:hidden` cross-origin iframe finish drawing (the mechanism is inferred, the result was seen in about 10 runs), so the hidden slot stayed on the Macedonian placeholder until shown. With `opacity: 0` it finished 3 of 3 times. `inert` keeps it out of the tab order and the accessibility tree. The headless runs of the final build were never completed; Filip checked it himself in his browser ("everything is alright").
- **EN/МК pill:** only the press scale (100 ms) transitions; the 150 ms colour and background fade from the shared `pressable` utility is switched off for `kvitSwitchLooks.option` (also used by `KvitThemeSwitch`, on purpose). The font weight never changed; the slow "bold" look was that fade.
- **Settings: Log out is always last, at the bottom, also on wide windows (Filip, 2026-10-03).** The old rule that lifted it under the other buttons from the `md` breakpoint up was removed.
- **`scripts/start-local.ps1`** (Filip asked for one script for everything, 2026-10-03): no switch starts the database, API (5018) and website (5173) in their own windows and opens the browser; `-Check` runs build, all tests and lint and stops at the first failure; `-Stop` closes both windows and stops the database container (data kept). Windows PowerShell 5.1.
